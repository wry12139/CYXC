## 1. 背景与目标

财小白当前是纯前端 PWA,所有学习数据(打卡、收藏、答题、难度档位、复习池)存在每个用户浏览器的 localStorage,彼此隔离,作者不可见。

用户的最终目标是三件事:**① 用户系统、② AI 问答、③ 后台按答题情况分层推送**。三者共享同一个后端地基,其中**用户系统是地基的地基**——没有账号,答题数据不知归属,后台无从推送,AI 对话也无从绑定。

**本次范围(聚焦地基,一次做稳一块):**
- ✅ 用户注册 / 登录(用户名 + 密码)
- ✅ 学习数据从本地"上云",跟账号走(跨设备同步的前提)
- ❌ AI 问答 —— 下一步做(但本设计的隐私铁律为其预留)
- ❌ 后台分层推送逻辑本身 —— 下一步做(本次只保证数据上云,让后台"有数据可读")

## 2. 核心设计理念:本地优先,登录增量上云

登录是**可选开关**,不是前提:

- **未登录**:一切照旧,数据在 localStorage,零改动、零风险,体验与现在完全一致。
- **已登录**:数据镜像到云端。写数据时本地 + 云端双写;登录/打开 App 时从云端拉取合并到本地。**本地永远是可用的那份**,云端是"跟人走"的备份 + 后台分层的数据来源。

好处:后端挂掉或断网时,已登录用户仍能continue使用(本地兜底),仅该次数据暂不同步。契合财小白"断网不白屏"原则。

## 3. 隐私铁律(贯穿全设计的硬约束)

用户明确要求:用户之间互相看不到在问什么/学什么/是谁;作者不能通过产品窥探某用户。落实为五条:

1. **user_id 严格隔离**:每行数据绑定 user_id;所有接口先验 token→解析身份→查询永远带 `WHERE user_id=当前登录用户`。用户 A 即使伪造请求也拿不到 B 的数据,因为后端只认 token 反查出的身份,**从不信任前端传来的 user_id**。
2. **无越权接口**:不提供"列出所有用户""查他人明细"的对外接口。后台分层是**服务器内部离线脚本**直接读库做聚合(如"user_42 正确率 60%→推 L2"),不经任何能查看明文对话/隐私的对外接口。
3. **密码只存加盐哈希**:`hashlib.pbkdf2_hmac`,永不存明文,作者也无法反推用户密码。
4. **后台只做聚合、不碰对话内容**:分层读的是学习表现统计(正确率/弱项主题),不是对话内容或真实身份。AI 对话(将来)默认不在服务器持久化,或仅按 user_id 加密隔离供用户自己回看。
5. **账号与真实身份脱钩**:用户名+密码,不强制真名/手机号。后台即便看到 user_42 的学习数据,也对应不到具体真人。

> 颗粒度界定:后台看到「user_42 正确率 60%,弱项基金」是分层必需、可接受;看到「能对上真人的某人问了 AI 什么」是要防的窥探。前者是聚合学习数据,后者是隐私内容,设计上二者不通。

## 4. 物理架构

三件事都在同一台内网服务器 `10.159.3.80`(用户 wangrenyi,RHEL9,已有 python3,刻意无 node/nginx):

```
浏览器(用户)
   │  ①访问前端            ②调后端 API
   ▼                        ▼
:8090 前端静态站       :8091 后端服务(新增)
（现有 http.server）    （新增 http.server + sqlite3）
                             │
                             ▼
                       finrookie.db(SQLite,新增)

同机现有:pipeline/(每日早报生成)、crontab、SSH 免密
```

- 后端语言 = **Python 标准库**(`http.server` + `sqlite3` + `hashlib` + `secrets`),延续服务器"零依赖"哲学,不装任何 pip 包。
- 后端独占端口 **8091**,前端 JS 通过 `http://10.159.3.80:8091/api/...` 调用。
- **CORS**:前端(8090)与后端(8091)端口不同,浏览器视为跨源,后端需返回 CORS 响应头允许前端调用。标准处理,非障碍。
- **内网 IP**:仅同局域网可访问,与"局域网内"需求一致。

## 5. 数据库设计(SQLite,3 张表)

```
users                         账号表
  id            INTEGER PK
  username      TEXT UNIQUE   登录名
  password_hash TEXT          pbkdf2 加盐哈希(绝不存明文)
  salt          TEXT          每人独立随机盐
  created_at    TEXT

sessions                      登录会话表
  token         TEXT PK       登录后发给前端的凭证(secrets 随机)
  user_id       INTEGER FK    属于谁
  created_at    TEXT
  expires_at    TEXT          过期时间

user_data                     学习数据表(每人一行)
  user_id       INTEGER PK
  data_json     TEXT          整棵 localStorage 状态树 JSON
  updated_at    TEXT          最后同步时间
```

**关键决策:`user_data` 整棵 JSON 存一个字段,不拆列。**
- 前端 store 现在就是"一个 JSON 对象",整存整取 → 前后端形状一致,改造量最小。
- 后台分层读出 JSON 解析 `progress.quizStats`、`difficulty.current` 即可,够用。
- 代价:无法用 SQL 直接查某字段。局域网小规模、分层在应用层算,不需要;将来真要复杂查询再拆表。

## 6. 后端接口清单(仅 6 个)

| 接口 | 方法 | 作用 | 隐私保证 |
|---|---|---|---|
| `/api/register` | POST | 用户名+密码,查重→存哈希 | 密码加盐哈希,不存明文 |
| `/api/login` | POST | 验证密码→发 token | 失败不透露是用户名错还是密码错 |
| `/api/logout` | POST | 作废当前 token | 只作废自己的 |
| `/api/sync/pull` | GET | 拉取我的云端数据 | `WHERE user_id=我` |
| `/api/sync/push` | POST | 上传我的学习数据 | 只能写自己那行 |
| `/api/me` | GET | 查我的账号信息 | 只返回自己 |

**无任何"列出/查他人"接口**(隐私铁律②)。后台分层是独立离线脚本读库,不在此对外接口内。

## 7. 鉴权流程(token 机制)

```
注册: POST /api/register {username, password}
      后端: 生成随机盐 → pbkdf2(password+salt) → 存 users

登录: POST /api/login {username, password}
      后端: 取该用户盐 → pbkdf2 比对
           一致 → secrets 生成 token,存 sessions(带过期)→ 返回 token
      前端: token 存 localStorage

后续同步: 请求头 Authorization: Bearer <token>
      后端: 查 sessions → 有效且未过期?→ 得 user_id
           → 所有数据操作只认这个 user_id(隔离的根)
           无效/过期 → 401 → 前端转未登录态(本地照常用)
```

**根基**:后端从不信任前端传来的 user_id(可伪造),只信任 token 反查出的 user_id。这是"A 拿不到 B 数据"的技术根本。

**密码安全**:
- `hashlib.pbkdf2_hmac`(带盐、多轮迭代),非简单 md5。
- token 用 `secrets.token_urlsafe()`(密码学安全随机)。

## 8. 前端改造

**原则:集中在 store 层,app.js 700 行业务逻辑几乎不动**(所有数据读写都过 store.get/set/update)。

```
js/auth.js    【新增】register/login/logout/token 管理 + 调后端
js/sync.js    【新增】pull(登录拉云端+合并) / push(数据变化传云端,防抖)
js/store.js   【小改】写操作后,若已登录,触发防抖 push(不阻塞 UI)
index.html    【小改】"我的"页加登录/注册入口 + 登录状态显示
js/app.js     【微改】init 时若有 token 就 pull;"我的"页显示登录态
```

**同步时机:**
- **登录成功**:pull 云端 → 与本地合并(见 §9)→ 之后正常用。
- **写数据时**(答题/收藏/打卡):照常写本地(即时);若已登录,防抖 2 秒 push 整棵 JSON。用户无感,失败不影响本地。
- **打开 App**:若已登录,pull 一次,拿到其他设备的最新数据。

## 9. 数据合并策略(智能合并)

场景:一台设备未登录攒了本地数据,登录同账号时云端也有数据,两份不一致。**取"更有利于用户"的并集**,登录只会让数据更完整、绝不丢失学习成果:

| 字段 | 合并规则 |
|---|---|
| `progress.streak` | 取较大值 |
| `progress.seenCardIds` | 并集 |
| `favorites.cards` / `favorites.terms` | 并集 |
| `review`(复习池) | 并集(按 quizId 去重;cleared 状态取"任一为 true 即 true") |
| `progress.quizStats`(attempts/correct) | 累加 |
| `difficulty.current` | 取较高档位(L3>L2>L1) |
| `user.tags` / onboarding | 取云端(已登录用户以账号设定为准);本地未 onboarded 则用本地 |

合并实现为**纯函数 `mergeState(local, remote)`**,配 node 断言测试,与现有 logic.js 风格一致。

## 10. 错误处理与边界

| 场景 | 处理 |
|---|---|
| 后端不可达 / 断网 | 已登录用户继续用本地;push 失败静默重试,pull 失败用本地兜底,不白屏 |
| token 过期/失效(401) | 前端转未登录态,提示"请重新登录",本地数据照常用 |
| 注册用户名已存在 | 后端返回明确错误,前端提示"用户名已被使用" |
| 登录密码错误 | 统一提示"用户名或密码错误"(不透露具体哪个错) |
| push 并发/防抖 | 整棵 JSON 覆盖式写入(最后写入者胜),防抖 2s 避免频繁请求 |
| SQLite 写入失败 | 后端返回 5xx,前端本地数据不受影响 |

## 11. 测试策略

- **纯函数**:`mergeState` 合并规则、密码哈希/校验往返、token 生成唯一性 —— node 断言(与现有 logic.js 验证方式一致)。
- **接口**:服务器上用 curl / python 脚本跑注册→登录→push→pull→登出全链路;重点验证**隔离**(用 A 的 token 拿不到 B 的数据、伪造 user_id 无效)。
- **前端集成**:局域网真机——未登录正常用 / 注册登录 / 双设备登录同账号看数据合并 / 断网降级。受工具限制,UI 端到端由用户本地手工确认。

## 12. 已知限制(诚实记录)

- **HTTP 非 HTTPS**:局域网内密码传输理论上可被同网嗅探,局域网可接受;**上公网必须加 HTTPS**。
- **单机 SQLite + http.server**:并发能力有限,局域网数十至上百用户够用;更大规模需换方案。
- **本次不含**:AI 问答、后台分层推送逻辑、密码找回(忘密码暂由作者后台手动重置)。
- **PRD 补录**:此功能不在原 PRD(V1.1)范围,建议后续作为 F-12 补入 §7 功能列表与 §12 迭代规划,并延续 §9 非目标范围的合规边界(不荐股、不交易)。
